# 기회 나무(OST) 만들기·점검 순서

「기회 나무 같이 만들어 줘」면 **만들기**, 「이 나무 점검해 줘」면 **점검**을 이 순서대로 한다.

말은 쉬운 말로 쓴다. 책 용어와 이렇게 맞춘다.

| 이 파일에서 쓰는 말 | 책 용어 |
|---|---|
| 맨 위 변화 | 목표 성과 |
| 어려움 | 기회 |
| 해결책 | 솔루션 |
| 작은 실험 | 가정 테스트 |

`(책 응용)` 이라고 적힌 줄은 책에 그대로 있는 말이 아니다. 혼자 일하는 사람에게 맞게 바꾼 것이다. 사용자가 「책에도 그래?」라고 물으면 그렇다고 밝힌다.

---

## 만들기 — 한 단계씩, 질문은 한 번에 하나

단계를 건너뛰지 않는다. 각 단계 끝에 지금까지 나온 나무를 짧게 보여 주고 다음 단계로 간다.

### 1. 맨 위 변화 한 문장 (Ch 3)
- 묻는다: 「이 서비스가 고객에게 만들어 줄 변화 하나는?」
- 매출보다 팀이 직접 움직일 수 있는 결과가 좋다(예: 연속 참여율, 평균 시청 시간).
- 특정 기능이 있어야 성립하는 문장(「앱 알림 사용률」)이면 산출물이다. 결과로 다시 쓰게 한다.

### 2. 어려움 3~5개 (Ch 5·6)
- 고객 말로 쓴다: 「~가 어렵다」「~하고 싶다」.
- 가지마다 **[들은 것] / [내 생각]** 을 붙인다. [들은 것]이면 어느 인터뷰에서 들었는지 묻는다. (책 응용)
- [내 생각]뿐인 가지는 「인터뷰 0건과 같다, 다음 인터뷰에서 확인할 것」이라고 알린다.

### 3. 어려움 다듬기 (Ch 6)
어려움마다 아래 넷을 본다. 하나라도 「아니오」면 고쳐 쓰게 한다.
1. 푸는 방법이 여러 개인가? 하나뿐이면 해결책이 섞인 것이다(「배우 이름 검색 기능」 → 「저 배우가 누구죠?」).
2. 고객이 실제로 할 법한 말인가? 회사 쪽 말이면 탈락.
3. 여러 고객에게서 나왔나? 한 명뿐이면 따로 두고 기다린다.
4. 풀면 맨 위 변화로 이어지나?

구조도 본다.
- 너무 크면 쪼갠다(「볼 만한가요?」 → 「누가 출연하나요?」「얼마나 긴가요?」).
- 아래 가지가 하나뿐이면 같은 말 반복이거나 형제가 빠진 것이다.
- 감정만 적힌 어려움(「답답하다」)은 왜 답답한지 다시 묻는다.

### 4. 풀 어려움 하나 고르기 (Ch 7)
- 「이걸 할까 말까?」로 묻지 않는다. 형제 어려움끼리 견준다: 몇 명이 얼마나 자주 겪나, 지금 해결 방법에 얼마나 불만인가.
- 맨 아래 가지 하나만 고른다.

### 5. 해결책 15~20개 쓰기 (Ch 8)
- 고른 어려움 하나 아래에만 쓴다.
- **사용자가 먼저 쓴다.** 그 목록을 보고 Codex 가 다른 종류의 해결책을 더 내고, 그걸 보고 사용자가 다시 쓴다. 15~20개가 될 때까지 번갈아 한다. (책 응용: 책의 「혼자 쓰기 ↔ 팀 공유」를 혼자 하는 사람에게 맞게 바꿈)
- 쓰는 동안에는 좋다·나쁘다를 말하지 않는다.
- 막히면 넓게 본다: 경쟁 서비스, 전혀 다른 분야, 고객 유형별(처음 온 사람·매주 오는 사람·멀리 사는 사람).
- 비슷한 것의 변형만 늘어나면 종류가 다른 것을 일부러 찾게 한다.

### 6. 나누기 — 지금 할 것 / 나중에 / 안 할 것 (Ch 8)
기준은 하나다: **이 어려움을 가장 잘 푸는가.** 멋진 것, 쉬운 것은 기준이 아니다.
1. 거르기: 이 어려움을 전혀 못 푸는 것 → **안 할 것**. 일부라도 풀면 남긴다.
2. 고르기: 가장 잘 푸는 것 중 서로 종류가 다른 3개 → **지금 할 것**. 하나로 좁히지 않는다.
3. 남기기: 나머지 → **나중에**. 지우지 않고 나무에 남긴다. (책 응용: 책은 「상위 3개」만 말한다)
- 팀이면 1인 3표 점 투표로 고른다(책 그대로).

### 7. 정리해서 보여 주기
아래 모양으로 한 번에 보여 준다.

```
맨 위 변화: ...
어려움
  - [들은 것] ...
  - [내 생각] ...
고른 어려움: ...
해결책 (N개)
  지금 할 것: 1) ... 2) ... 3) ...
  나중에: ...
  안 할 것: ...
다음 할 일
  - [내 생각] 가지를 다음 인터뷰에서 확인
  - 지금 할 것 3개를 작은 실험으로 견주어 하나로 좁히기 (Ch 9·10)
```

### 8. 한 장 그림으로 그리기
7단계를 보여 준 뒤 묻지 않고 바로 그린다. 「그림으로 그려 줘」「나무 그려 줘」라고 해도 이 단계를 한다.
1. 이 스킬 폴더의 `ost-tree-template.html` 을 읽는다.
2. 틀을 그대로 복사해 사용자가 지금 있는 폴더에 `기회나무-YYYY-MM-DD.html` 로 저장한다. 그다음 **`<script type="application/json" id="ost-data">` 안의 JSON 만** 이번 나무 내용으로 바꾼다. 나머지 HTML·CSS·JS·주석은 한 글자도 고치지 않는다. 틀에 들어 있는 12KM 예시는 남기지 않는다.
   - `opportunities` 의 `source` 는 `"heard"`(들은 것) 또는 `"mine"`(내 생각). 들은 것이면 `count` 에 사람 수.
   - `picked: true` 는 고른 어려움 하나에만. 다른 어려움 아래 보관한 해결책은 그 어려움의 `keep` 에.
   - `solutions` 는 6단계에서 나눈 그대로 `now` / `later` / `drop`. 칸이 비면 빈 배열.
   - 글은 짧게: 카드 한 장에 한 줄(20자 안팎). 설명이 더 필요하면 `note` 에.
3. 저장한 뒤 JSON 이 맞는지 확인한다: `python3 -c "import re,json,sys;s=open(sys.argv[1]).read();json.loads(re.search(r'id=\"ost-data\">(.*?)</script>',s,re.S).group(1));print('OK')" <파일>`. 실패하면 고쳐서 다시 확인한다.
4. 저장한 파일 경로를 알려 주고, macOS 면 `open <파일>` 로 연다(Windows 는 `start`).
5. 아직 6단계(나누기)를 안 했으면 해결책 칸은 비워 두고 「해결책은 아직」이라고 알린다.

## 점검 — 이 순서로 보고, 항목마다 ✅ / ⚠️ + 고칠 문장

1. **맨 위**: 결과인가, 기능·매출인가?
2. **어려움이 고객 말인가**: 회사 쪽 말, 감정만 적힌 말이 있나?
3. **해결책이 어려움 자리에 섞였나**: 푸는 방법이 하나뿐인 가지
4. **근거 표시**: [들은 것] / [내 생각] 이 붙어 있나? [내 생각]뿐인 가지는 몇 개인가?
5. **구조**: 아래 가지가 하나뿐인 줄, 위 가지가 둘인 것, 서로 겹치는 형제
6. **해결책 수**: 고른 어려움 하나에 15~20개인가? 어려움마다 해결책이 하나씩만 달려 있으면 나무가 아니라 할 일 목록이다.
7. **나누기**: 지금 할 것이 3개이고 서로 종류가 다른가? 고른 기준이 「가장 잘 푸는가」인가? 나중에 칸을 지우지 않았나?

마지막에 **「가장 먼저 고칠 것 1개」** 를 한 줄로 쓴다. 사용자가 그림을 원하면 고친 나무로 만들기 8단계를 한다. 단계가 빠져 있으면(예: 해결책을 아직 안 씀) 점검을 거기서 멈추고 「만들기 5단계부터 이어 하자」고 제안한다.
